---
笔者所在的项目组，主要负责视频课程在线制作，用户在前台使用UI选择元素并定义动效行为，系统生成预期的视频课程。平台迭代过程中，不断有音视频处理的需求，比如视频合成、背景音以及字幕等。笔者受命搭建音视频处理服务，在设计伊始，笔者便将服务定位成一个为各业务方提供音视频处理能力的“底层”服务，在扩展性、可用性以及执行效率上下了一些功夫，最终效果也符合预期。笔者将从系统设计、技术选型、扩展性设计、性能优化四个方面进行介绍。  

系统设计
====
整体设计如图所示：
<img src="http://glsp-img.unipus.cn/glsp/prod/public/avatar/image/20250703/%E9%9F%B3%E8%A7%86%E9%A2%91%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1.jpg" height = "800" width="100%"/>

系统分为三层：接入层、存储层和执行层。接入层负责对接各业务方，职责包括提供API接口、授权与鉴权、限流，逻辑比较简单，将通过校验的任务数据保存存储层。存储层职责是存储任务数据。执行层实现绝大部分逻辑，包括读取并解析任务数据，选择相应的执行器来处理任务数据，并将最终结果更新到存储层。  

技术选型
====
音视频服务，采用springboot + java + MoviePy + Python 实现。由系统设计介绍可知，从编码实现的角度来讲，系统可分为两个部分：业务部分和任务处理部分。业务部分和常规web服务一样，采用最通用的 springboot + java 组合。音视频任务处理部分，笔者最终选择MoviePy。MoviePy是一个将FFMpge进行封装，为用户提供各种音视频处理能力 api的Python框架。笔者为什么要选择MoviePy呢？  

首先，对音视频进行处理，首选语言应当是Python，而不是Java。具备音视频处理经验的读者应当有体会，经常需要处理视频中特定帧的特定部分，对这种多维数组处理Python仅需一两行代码。其次，基于Python的一些相关框架很多，如处理数组的Numpy、处理图像的PIllow和cv2、绘制各种形状的matplotlib.pyplot，这是都是音视频处理所需要的能力，反观Java相关框架寥寥无几并且有些社区不再活跃更新。最后，MoviePy的Api简洁简单，提供遮罩能力，可以实现较为复杂的动效效果。  

扩展性设计
====
音视频服务作为一个底层服务，笔者尤其重视扩展性的设计。笔者认为，扩展性主要考虑两点：
* 音视频服务后续迭代方向，是不断提供新的处理能力。当新处理能力开发完毕，如何更快捷方便的部署，笔者称之为代码扩展性
* 作为底层服务，对发生上游流量增加导致任务堆积时，如何快速提升系统处理能力，笔者称之为系统扩展性

代码扩展性设计
----
在技术选型中介绍，系统Web部分使用java + springboot实现，音视频处理部分使用python + moviePy来实现。笔者对代码扩展性的预期是，当相应能力的脚本开发完毕，将脚本存放到指定路径即可，服务无需频繁发布。这样开发人员只需专注于脚本开发和接口文档编写，而不用每开发完一个脚本，都要进行相应的业务逻辑编写。  

提供不同能力的脚本，所需要的参数分为两类：可变参数和固定参数。固定参数包括文件处理类型、生成文件名称以及文件编码。可变参数包括脚本运行所需参数。服务提供请求体如下：
```
public class CommonParam {
    @ApiModelProperty("音视频处理类型，参见SupportedAnimationType”, required = true)
    private String animationType;

    @ApiModelProperty("音视频处理参数”, required = true)
    private String param;

    @ApiModelProperty(value = "返回的结果类型，eg mp4、wepm、mp3”, required = true)
    private String type;

    @ApiModelProperty(value = "使用的编码")
    private String code;

    @ApiModelProperty(value = "文件名")
    private String fileName;
}
```

其中animationType 用于确定任务分发时使用的执行器。这样设计之后，当开发新的处理能力如从视频中提取音频，只需新增一行配置即可(笔者服务配置在Apollo中)。如下所示：
```
{
    "operationType": "ExtractAudio",
    "script": [
        "ffmpeg",
        "-i",
        "{videoUrl}",
        "-vn",
        "-acodec",
        “{code}",
        "{-b:a rate:128k}",
        "{resFile}"
    ]
}
```
配置完毕，业务方即可使用如下请求体来使用音频提取能力，系统会自动下载videoUrl存储到本地，并替换脚本中的占位符。  
```
{
    "animationType": "ExtractAudio",
    "param": {
        "videoUrl": "https://glsp-img.unipus.cn/glsp/dev/public/material/video/20241018/56fbf7b99f069d43d1d1256a6dd39f7c.mp4",
        "rate": “64k"
    },
    "type": "mp3",
    "code": "libmp3lame"
}
```

系统扩展性设计
----
作为一个底层服务，当上游流量突然增加，除了限流来保护服务免于宕机之外，还需要考虑如何快速提升服务吞吐量，为业务方提供稳定处理能力。对于系统扩展性，笔者设计的预期是，当流量增加需要扩充处理能力时，运维仅仅需要做的是增加机器，无需任何其他操作。  

笔者最初设计方案是接入层保存任务数据之后，通过MQ发送消息，执行层从MQ接收消息进行处理。如下所示：
<img src="http://glsp-img.unipus.cn/glsp/prod/public/avatar/image/20250703/MQ.jpg" height = "570" width="100%"/>

这种设计，在实践中暴漏了一些问题。首先，当需要对系统处理能力进行提升时，不仅需要对服务实例进行扩充，还需要对MQ对接进行扩充，与设计预期有一定的差距。而且，在进行扩充时，会触发Rebalance，会导致信息消费暂停。最为严重的是，会导致消息处理负载不均衡，任务处理时间超长的隐患。MQ的负载均衡粒度是对任务而言，然而在笔者的场景中，理想的负载均衡应当是按照任务处理时间来进行均衡的。比如任务A、B、C、D的处理时间分别为T1、T2、T3、T4，其中T1=(T2+T3+T4)，将这四个任务发送给2个队列Q1和Q2，MQ实现的负载均衡是是每个队列分配两个，这样队列Q2的消费者空闲时，在Q1的B任务还处于排队状态。更理想的分配方式是将任务A分配队列Q1，任务B、C、D分配Q2，这样才能充分利用系统处理能力。  

笔者改进了设计方式，为每个服务实例维护一个固定大小线程池，线程轮询从数据库获取任务数据进行处理。只要数据库中存在待处理的任务，无论哪个服务实例中线程都可能会拉取处理，不会存在一个消费的任务在堆积，其它消费者处于空闲等待状态，伪代码如下所示：
```
        int concurrency = Runtime.getRuntime().availableProcessors();
        concurrency = concurrency > 1 ? concurrency - 1 : concurrency;

        ExecutorService fixedThreadPool = Executors.newFixedThreadPool(concurrency, runnable -> {
            Thread thread = new Thread(runnable);
            thread.setName("animation-task" + thread.getId());
            return thread;
        });
        for (int x = 0; x<concurrency;x++) {
            fixedThreadPool.submit(() -> {
                try{
                    while (true) {
                        // 获取任务数据
                        MediaTaskInfo mediaTaskInfo = mediaTaskInfoRepository.getWaitingTask();
                        if (Objects.isNull(mediaTaskInfo)) {
                            // 没有任务，休息5s
                            try {
                                TimeUnit.SECONDS.sleep(5);
                            } catch (InterruptedException ignored) {


                            }
                            continue;
                        }
                        // 更正任务状态
                        bool res = updateStatus();
                        If (!res) {
                            // 更新状态失败，说明其他消费者处理，返回
                            continue;
                        }
                        // 正式处理任务
                        mediaTaskService.classifiedExecuteMediaTask(mediaTaskInfo);
                    }
                } catch (Exception e) {
                    // 任何情况，消费者不能退出
                    log.error("excute task error", e);
                }
            });
        }
```

性能优化
====
服务上线部署一段时间后，暴漏了一些性能问题，主要有以下两类：
1. 服务实例资源告警，内存和cpu都紧张
2. 视频合成任务处理时间过长

在服务告警时，笔者登录服务实例查看，服务器中有java、pyhon3和FFMpeg进程(MoviePy底层依赖FFMpeg)。并且由于服务器资源紧张，相同的脚本和参数，在不同服务器上运行时间差别很大。由此可见，服务资源告警和任务处理时间存在一定的因果关系。  
<img src="http://glsp-img.unipus.cn/glsp/prod/public/avatar/image/20250703/top.png" height = "500" width="100%"/>

笔者发现，内存占用最多的是java进程，cpu使用率最低，而负责音视频处理的Python和FFMpeg分配得到的内存较少，cpu使用率较高。结合服务场景，java的处理逻辑相对简单，主要的处理任务是由Python和FFMpeg完成。因此，笔者首先采取的措施是，为服务实例申请更大的内存(8G)和更多的核数(4)，同时只给java服务分配较少的内存(1G)。配置完毕，服务资源告警消失，任务处理时间有一定的提升。  

然而视频合成任务的时长仍然不达预期，需要进一步优化。视频合成具体场景是业务方通过Api指定，特定元素在特定的时间段执行特定的动效行为，比如出入场、跳跃以及模糊等，这些效果将在最终生成的课程视频中得以显现。笔者具体分析了几个执行时间较长的任务处理数据，从中发现了一些问题。如下所示，是一个合成时长71s，分辨率1920*1080的课程视频任务数据，视频合成任务数据大抵如此，正常结构体较大，笔者只筛选一些共性部分:

第一个元素是作为背景，图片或者颜色，生命周期和视频时间一样。第二个元素是数字人，分辨率和生成视频一样，数字人视频讲解课程内容。其余部分为字幕，无动效。  

笔者技术选型选择MoviePy，原因之一是动效实现，MoviePy比FFMpeg简洁的多。同时笔者也发现, 同样的动效，MoviePy比FFMpeg时间消耗也要大得多。因此笔者采取的第二个措施是，将一些数量多或者存活时间久，没有动效，在最底层或者最顶层的元素合成，由FFMpeg实现。其中最符合条件的元素就是背景和字幕。背景合成的思路时，视频合成过程背景元素不参与，合成结束背景直接“拓印”上去。字幕合成的思路，是将字幕数据转成一个srt字幕文件，在视频合成结束之后，由FFMpeg一次性合成。这个措施，对视频合成任务处理时长取得了良好的效果。  

笔者在查看元素时，发现数字人视频分辨率和视频一样大，但是数字人本身占据的空间并不大，其余部分为透明，如下所示(为演示效果，将背景改为黄色，否则是纯黑色)。因此笔者的第三个措施是，对数字人视频数字人部分进行裁剪，只将裁剪后的视频参与合成，合成效率有一定的提升。

笔者在观察合成任务处理数据结构定义，发现当前的定义是按照元素在视频中的层次从上向下定义的，这样定义虽然直观明了，却可能元素重复加载的问题，比如一个元素在时间段(T0~T1) 有一个进场动效，在时间段(T2 ~ T3) 又有一个出场动效。此时同一个元素，就会被重复加载两次，结合措施二，最终笔者将任务处理数据结构调整为如下：

最后，笔者发现视频合成的帧率是25fps，笔者依据经验25fps是一个在电视剧、电影中的常用帧率。在课程制作的场景中，为了保证教学效果，一般不会如此高频的切换元素，对授课用户也无必要。经和产品沟通，原来是客户的标书要求，只需要最终视频的帧率是25fps即可，于是笔者将视频合成的帧率由25fps，调整到20fps(15以上应该都行，笔者没有太过激进)，视频生成完毕最后来一次转换。调整之后视频合成效率提升20%。  

综上所述笔者针对性能问题，主要采取了四个措施：
1. 申请更大的内存和更多的cpu，只给java服务分配较少的资源，主要资源给MoviePy和FFMpeg进行任务处理
2. 动静分离，将没有动效的一些元素，改为由FFMpeg实现
3. 数字人视频，裁剪出数字人部分，避免整个视频参与合成
4. 调整任务处理数据结构，避免元素重复加载，减小视频合成的内存消耗。同样的资源，可以允许更多的任务并行处理
5. 调低视频帧率，由25fps下降到20fps

最终，T时长的视频合成任务，耗时由之前的(3~4)T，下降到(1~1.5)T。  

笔者曾对一些服务进行系统性的优化，最大的一个感受是优化是一项技术和业务相结合的能力。在本次实践中，调整任务处理方式，避免任务等待。修改任务处理数据结构，避免元素重复加载，就是技术层面。将元素列表，结合业务场景，划分为背景、数字人和字幕，针对特定的场景去优化，就是业务层面。这对系统设计者也是一个挑战，过度的关注业务，会导致服务与业务耦合，通用性下降。然而过度从业务抽象，可能导致一些依赖业务的优化无法进行。
